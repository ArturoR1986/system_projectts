# 06_Load_Bearing_Compression

## Purpose

The Load-Bearing Compression module compresses prompts, systems, workflows, modules, or instruction sets without breaking the behavior that makes them work.

Use this module when a system has become too long, repetitive, bloated, or hard to maintain, but the spirit, function, identity, and practical intelligence must be preserved.

The goal is not to make the material short.

The goal is to make it clearer, stronger, and easier to use while preserving the load-bearing elements.

Core rule:

```text
Distill, do not shrink.
```

## Core Function

Load-Bearing Compression asks:

- What makes this system work?
- Which parts are structurally necessary?
- Which parts only repeat, decorate, or explain?
- What behavior must survive compression?
- What spirit or identity must be preserved?
- What boundaries are essential?
- What can move into sources, templates, examples, or modules?
- What should remain always-on?

## Use When

Activate this module when:

- a prompt is too large
- a system prompt has grown past its useful active size
- instructions repeat the same behavior many times
- a framework needs to become modular
- the user wants to preserve “spirit” while reducing size
- the system needs clearer behavior language
- a long workflow needs to become a shorter SOP
- source material must be split into modules
- the user says the prompt has become too big to run all the time
- the system needs to distinguish core instructions from reference material

## Inputs Needed

Use the available material first.

Helpful inputs include:

- the original prompt, workflow, or instruction set
- the target use case
- the intended user
- what must be preserved
- what feels bloated or repetitive
- where the compressed version will live
- whether the output is for Project Instructions, Project Sources, a module, or a reusable template

Ask follow-up questions only when the preservation target is unclear.

## Load-Bearing Elements

Preserve these elements during compression:

### 1. Core Purpose

The reason the system exists.

### 2. Desired Behavior

What the assistant should consistently do.

### 3. Operating Principles

The rules, values, or decision logic that shape behavior.

### 4. Workflow Logic

The sequence of actions that makes the system reliable.

### 5. Safety and Epistemic Boundaries

Truth, privacy, agency, uncertainty, evidence separation, symbolic containment, and compliance boundaries.

### 6. Distinctive Identity

The system’s voice, role, practical imprint, and recognizable intelligence.

### 7. Output Structure

The formats, sections, templates, or response shapes that make the system usable.

### 8. User-Facing Usefulness

The practical value the user receives.

## Compressible Elements

Reduce or move these elements:

- repeated instructions
- duplicate principles
- long explanations that do not change behavior
- decorative philosophy
- vague inspiration
- redundant examples
- repeated warnings
- over-specified tone instructions
- examples that belong in templates
- domain-specific details that belong in source modules
- long edge-case lists that belong in test cases or reference files

## Process

Use this sequence:

### 1. Identify the System Type

Classify the material as one or more of:

- core prompt
- source manual
- workflow
- module
- template
- test file
- domain-specific extension
- philosophical or identity layer

This determines what should stay active and what should move into sources.

### 2. Extract Load-Bearing Elements

Identify what must survive.

Use the eight load-bearing categories:

- purpose
- behavior
- principles
- workflow
- boundaries
- identity
- output structure
- usefulness

### 3. Identify Compression Opportunities

Find repetition, duplicate rules, decorative text, and details that can be moved elsewhere.

### 4. Preserve Spirit

Run a spirit check:

- What is the deeper intent?
- What behavior does the language create?
- What identity signal must remain?
- What practical imprint must survive?
- What wording carries the system’s voice?

### 5. Compress the Material

Rewrite in clearer, shorter, action-oriented language.

Use Positive Compression when instructions are negative, vague, or defensive.

### 6. Route the Depth

Decide what belongs in:

- active Project Instructions
- Project Sources
- individual modules
- output templates
- test cases
- examples
- domain modules

### 7. Test the Compression

Use the three compression tests:

#### Behavior Test

Does it still act correctly?

#### Spirit Test

Does it still feel like the same system?

#### Utility Test

Is it easier to use, not merely shorter?

## Boundaries

Do not compress by deleting meaning.

Do not flatten identity into generic assistant behavior.

Do not remove safety, privacy, agency, or epistemic boundaries.

Do not remove workflow logic if it is what makes the system reliable.

Do not move essential behavior into a source file if it must always shape the response.

Keep hard rules when they protect safety, ethics, compliance, factual integrity, privacy, or user agency.

## Common Pairings

### Positive Compression

Use when negative or defensive wording needs to become clear behavior targets.

### Prompt Audit

Use before compression to diagnose what works, what weakens behavior, and what must be preserved.

### ENL Symbolic Pattern Engine

Use when the system’s spirit, symbolic language, or identity imprint must be preserved.

### Architect Gate

Use when deciding whether the material is a core system, source manual, module, or workflow.

### Output Templates

Use when examples or repeated structures should move out of the active prompt.

### Test Cases

Use after compression to verify that behavior, spirit, and utility were preserved.

## ENL/L Spirit Preservation

This module is central to ENL 3.0.

ENL/L material often carries meaning through big language, symbolic direction, emotional pacing, practical experience, and identity signals.

Load-Bearing Compression must preserve that living imprint.

It should not treat all long language as bloat.

Some long language is doing real work.

Before reducing it, identify the work it performs.

Then translate that work into:

- behavior
- module rules
- routing logic
- output structure
- examples
- tests
- source references

The best compression makes the system feel more itself, not less.

## Final Operating Rule

Preserve what makes it work.

Move what does not need to run.

Distill, do not shrink.
