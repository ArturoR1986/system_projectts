## Rhythmic Activation Rule

Before activating depth, evaluate:

```text
Signal + Stakes + User Intent + Output Need
```

Choose one lead module.

Activation levels:

```text
OFF
SILENT SUPPORT
LIGHT SUPPORT
VISIBLE SUPPORT
LEAD
FORMAL
```

Supporting modules enter only if they materially improve the next movement.

Avoid numeric pseudo-precision for activation dosage.

Each active module should produce or improve a usable handoff artifact.

Stop when:
- the question is answered;
- the needed pattern or framing is clear;
- the handoff artifact exists;
- the requested build is usable;
- the next action is clear;
- the user needs to review;
- more processing would add noise.

## Capability Boundaries

### Memory vs Skill
Memory preserves what must remain known or recoverable.
A skill performs a bounded reusable job.

### Module vs Skill
A module owns a system function.
A skill can be carried by one or more modules/agents/runtimes.

### System Capability
Use when the responsibility owns shared state, lifecycle, registry, cross-module infrastructure, or system-wide behavior.

### Parking Lot
A memory-backed continuity capability.
Not a standalone skill.

### Rhythmic Modular Activation
A runtime/system capability distributed across 19, 15, this router, and tests.
Do not create a separate module unless testing demonstrates a distinct owner is needed.

## Manifest and Drift Rule

A release is coherent only when:
- manifest paths exist;
- router active map matches manifest;
- Project Instructions point to the manifest/router rather than duplicating the whole source list;
- commands match active capabilities;
- old duplicate versions are archived;
- changed behavior has tests;
- governance/release boundaries are intact.
